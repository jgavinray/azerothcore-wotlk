# AzerothCore Multi-Threaded Architecture Restructuring

## Document Purpose

This document captures the architectural analysis and incremental migration path for transforming AzerothCore from a single-threaded game loop to a multi-threaded architecture. It is designed to be used as a reference for breaking down work into manageable scopes that can be assigned to development teams or AI assistants.

---

## 1. Current Architecture Overview

### 1.1 Core Design

AzerothCore uses a **hybrid threading model**:

| Component | Threading Model | Notes |
|-----------|-----------------|-------|
| World Game Loop | Single-threaded | All game logic updates run sequentially |
| Network I/O | Multi-threaded | Boost.Asio with configurable pool |
| Database | Async with worker pools | Configurable async/sync connection pools |
| MapUpdater | Multi-threaded | Pathfinding and movement calculations |

### 1.2 The Single-Threaded Constraint

The main game loop (`World::Update()`) is single-threaded because:

1. **Global Singletons** - Dozens of managers (sWorld, sObjectMgr, sScriptMgr, sMapMgr, etc.) are accessed without synchronization
2. **Shared Data Structures** - Map grids, creature lists, player sessions, and object registries are not thread-safe
3. **Creature AI** - AI state machines modify creature data without internal locking
4. **Script System** - Lua/Embedded script interpreters are not thread-safe
5. **Reference Iteration** - Iterating over players, creatures, and objects assumes no concurrent modification

### 1.3 Existing Multi-Threaded Infrastructure

The codebase already has proven threading patterns:

| Subsystem | Location | Status |
|-----------|----------|--------|
| Database Worker Pool | src/server/database/ | Fully operational |
| MapUpdater | src/server/game/Maps/ | Fully operational for pathfinding |
| Network Threads | src/server/shared/Network/ | Fully operational |
| MPSCQueue | src/common/Threading/ | Lock-free queue available |
| TaskScheduler | src/common/Utilities/ | Async task support exists |

## 2. Incremental Migration Strategy

### 2.1 Philosophy: "Islands of Concurrency"

Rather than a complete rewrite, the approach is to:

1. **Identify naturally isolated subsystems** that can run independently
2. **Add thread-safety incrementally** to each subsystem
3. **Expand existing islands** rather than creating new ones from scratch
4. **Maintain backward compatibility** - single-threaded mode remains default

### 2.2 Why Incremental Works

- Maps are naturally partitioned (each map/instance is isolated)
- Existing locking primitives (std::mutex, std::shared_mutex) are already used in some areas
- MapUpdater proves the worker pool pattern works
- Database async pool proves cross-thread communication works
- No need to rewrite core logic - add threading around existing code

### 3.2 Code Hygiene: Compilation Warnings

**Current State:** The codebase is configured to **ignore compiler warnings**.

| Setting | Current Value | Implication |
|---------|---------------|-------------|
| `WITH_WARNINGS` | OFF (default) | All warnings suppressed |
| `TREAT_WARNINGS_AS_ERRORS` | Not configured | Warnings do not block builds |

**Why This Is a Problem:**

1. **Hidden bugs** - Warnings often indicate real issues (unused variables, type mismatches, potential null dereferences)
2. **No quality gate** - New code with warnings can be merged without detection
3. **Threading work will be buried in noise** - Any new warnings from threading changes will be invisible
4. **Technical debt accumulation** - Warnings ignored today become bugs tomorrow

**What Needs to Happen:**

1. **Enable warnings** - Set `WITH_WARNINGS=ON` in CMake configuration
2. **Treat warnings as errors** - Add `-Werror` flag for CI builds
3. **Fix existing warnings** - Clean the codebase before adding new complexity
4. **CI enforcement** - Fail builds on new warnings

**Recommended CMake Configuration:**
```cmake
option(WITH_WARNINGS       "Show all warnings during compile" ON)
option(TREAT_WARNINGS_AS_ERRORS "Treat warnings as errors in CI" ON)
```

**Warning Categories to Address:**
- Unused variables and parameters
- Implicit type conversions
- Missing return statements
- Unused function parameters (common in virtual overrides)
- Deprecated API usage
- Potential null pointer dereferences
- Sign comparison warnings

**Risk Level:** High - Without clean compilation, threading bugs will be hidden in warning noise.

**Timeline:** 2-4 weeks to clean existing warnings and establish enforcement.

## 11. Design Pattern References

This section provides references and explanations for the design patterns mentioned throughout this document. Teams unfamiliar with these patterns should review them before beginning work.

### 11.1 Islands of Concurrency Pattern

**Concept:** Instead of making the entire application multi-threaded at once, identify naturally isolated subsystems ("islands") that can run concurrently without interfering with each other. Each island manages its own threading internally while presenting a simplified interface to the rest of the system.

**Key Characteristics:**
- Each island has a single entry point for work submission
- Islands do not share mutable state directly; they communicate via message queues or well-defined interfaces
- Islands can be developed, tested, and deployed independently
- The system can run with islands in single-threaded mode for backward compatibility

**Why This Applies Here:** Maps, instances, and battlegrounds are naturally isolated. Each map's state is mostly independent, making them ideal candidates for separate thread pools.

**References:**
- "Islands of Concurrency" - Various industry implementations (e.g., Unity's ECS, Unreal's Game Thread)
- Martin, R. C. (2009). *Clean Architecture*. Chapter on concurrency boundaries.
- Real-world examples:
  - [Unity DOTS/ECS Architecture](https://docs.unity3d.com/Packages/com.unity.entities@latest)
  - [Unreal Engine Game Thread and Render Thread](https://docs.unrealengine.com/)

---

### 11.2 Worker Pool Pattern

**Concept:** A fixed pool of worker threads pulls work from a shared queue and processes it. The main thread submits work to the queue and does not wait for completion (fire-and-forget) or waits via future/promise.

**Key Characteristics:**
- Fixed number of worker threads (configurable)
- Work items are queued and distributed among workers
- Workers run independently and continuously
- Clean shutdown via cancellation tokens or poison pills

**Existing Implementation in Codebase:**
- `src/server/database/Database/DatabaseWorkerPool.h` - Database worker pool
- `src/server/game/Maps/MapUpdater.h` - Map update worker pool

**References:**
- Goetz, B. et al. (2006). *Java Concurrency in Practice*. [Chapter 8: Threads](https://javaconcurrencyinpractice.com/)
- C++11 `std::thread` pool implementations:
  - [cppreference - std::thread](https://en.cppreference.com/w/cpp/thread/thread)
  - [CppCon Talk: Thread Pools](https://www.youtube.com/results?search_query=cppcon+thread+pool)
- [Boost.Asio Documentation](https://www.boost.org/doc/libs/release/doc/html/boost_asio.html)

---

### 11.3 Producer-Consumer Queue

**Concept:** A thread-safe queue where producer threads add work items and consumer threads remove and process them. Decouples work submission from work execution.

**Key Characteristics:**
- Thread-safe insertion and removal
- Blocking operations when queue is empty (for consumers)
- Bounded or unbounded capacity
- Optional priority ordering

**Existing Implementation in Codebase:**
- `src/common/Threading/PCQueue.h` - Mutex-based producer-consumer queue
- `src/common/Threading/MPSCQueue.h` - Lock-free MPSC (Multi-Producer Single-Consumer) queue

**References:**
- Goetz, B. et al. (2006). *Java Concurrency in Practice*. [Chapter 8: Threads](https://javaconcurrencyinpractice.com/)
- Dmitry Vyukov's MPSC queue:
  - [1024cores: MPSC Queue](http://www.1024cores.net/home/lock-free-algorithms/queues)
  - [1024cores: Unbounded MPSC](http://www.1024cores.net/home/lock-free-algorithms/queues/unbounded_mpsc)

---

### 11.4 Lock-Free Queue (MPSC)

**Concept:** A queue implementation that uses atomic operations instead of locks, allowing multiple producers to add items concurrently while a single consumer removes them without blocking.

**Key Characteristics:**
- No mutexes or locks required
- Uses atomic operations with memory ordering
- Higher throughput for high-contention scenarios
- Typically single-consumer only (for multi-consumer, use MPMC variants)

**Existing Implementation in Codebase:**
- `src/common/Threading/MPSCQueue.h` - Dmitry Vyukov's lock-free MPSC queue

**References:**
- Vyukov, D. "Bounded and Unbounded MPSC Queue." [http://www.1024cores.net/home/lock-free-algorithms/queues](http://www.1024cores.net/home/lock-free-algorithms/queues)
- Herrihy & Shavit, *The Art of Multiprocessor Programming*. [O'Reilly](https://www.oreilly.com/library/view/the-art-of/9780123973375/)
- [C++ Atomics Documentation](https://en.cppreference.com/w/cpp/atomic/atomic)

---

### 11.5 Reader-Writer Lock (std::shared_mutex)

**Concept:** A synchronization primitive that allows multiple concurrent readers or a single writer. Optimized for read-heavy workloads.

**Key Characteristics:**
- Multiple threads can hold shared (read) locks simultaneously
- Exclusive (write) lock is mutually exclusive with all other locks
- Writers may starve readers or vice-versa depending on implementation

**Existing Implementation in Codebase:**
- `src/server/game/Globals/ObjectAccessor.h` - Uses std::shared_mutex for player lookups
- `src/server/game/Maps/Map.h` - MMapLock uses std::shared_mutex

**References:**
- C++17 `std::shared_mutex` and `std::shared_lock` documentation:
  - [cppreference - std::shared_mutex](https://en.cppreference.com/w/cpp/thread/shared_mutex)
  - [cppreference - std::shared_lock](https://en.cppreference.com/w/cpp/thread/shared_lock)
- Goetz, B. et al. (2006). *Java Concurrency in Practice*. [Chapter 4: Objects](https://javaconcurrencyinpractice.com/)

---

### 11.6 Work Stealing

**Concept:** Each worker thread has its own work queue. When a thread's queue is empty, it "steals" work from another thread's queue. Balances load dynamically.

**Key Characteristics:**
- Reduces contention compared to a single shared queue
- Improves cache locality (threads work on their own queues)
- More complex to implement correctly
- Used in Intel TBB, Java Fork-Join framework

**References:**
- Leiserson, C. E. (2009). "Work-Stealing Thread Pools." [MIT CSAIL Paper](https://people.csail.mit.edu/cel/papers/popl09.pdf)
- Intel Threading Building Blocks (TBB): [Official Documentation](https://intel.github.io/oneapi-tbb/)
- Cilk Plus Work Stealing: [Cilk Documentation](https://cilk.github.io/)
- [CppCon Talk: Work Stealing](https://www.youtube.com/results?search_query=cppcon+work+stealing)

---

### 11.7 Round-Robin Work Distribution

**Concept:** Work items are distributed to worker threads in a cyclic order. Simple and predictable load balancing.

**Key Characteristics:**
- Each thread gets approximately equal work
- Easy to implement with atomic counter
- May not adapt to varying work item complexity

**References:**
- Round-Robin scheduling: [Wikipedia](https://en.wikipedia.org/wiki/Round-robin_scheduling)
- [Thread Pool Patterns](https://en.wikipedia.org/wiki/Thread_pool)

---

### 11.8 CPU Affinity

**Concept:** Binding specific threads to specific CPU cores. Can improve performance by reducing context switching and improving cache utilization.

**Key Characteristics:**
- Threads run only on designated cores
- Can reduce cache misses for CPU-intensive workloads
- Requires OS-level support

**Existing Implementation in Codebase:**
- `UseProcessors` configuration option in worldserver.conf.dist and authserver.conf.dist

**References:**
- Linux `pthread_setaffinity_np()`: [man7.org](https://man7.org/linux/man-pages/man3/pthread_setaffinity_np.3.html)
- Windows `SetThreadAffinityMask()`: [Microsoft Docs](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setthreadaffinitymask)
- CPU Affinity overview: [Wikipedia](https://en.wikipedia.org/wiki/Processor_affinity)

### 11.9 Lock Granularity

**Concept:** The scope of data protected by a single lock. Coarse locking (large scope, fewer locks) is simpler but reduces concurrency. Fine locking (small scope, more locks) increases concurrency but adds complexity and deadlock risk.

**Levels:**
- **Coarse:** Single global lock for entire subsystem
- **Medium:** Per-component locks (e.g., one per map)
- **Fine:** Per-element locks (e.g., one per grid cell)

**Trade-offs:**
- Coarse: Simpler, less concurrent, lower overhead
- Fine: More concurrent, more complex, higher overhead, more deadlock risk

**References:**
- Goetz, B. et al. (2006). *Java Concurrency in Practice*. [Chapter 10: Lock Granularity](https://javaconcurrencyinpractice.com/)
- [Lock Striping Pattern](https://en.wikipedia.org/wiki/Striped_lock)

### 11.10 Message Queue for Cross-Subsystem Communication

**Concept:** Subsystems communicate by sending messages through queues rather than direct function calls. Decouples components and enables asynchronous processing.

**Key Characteristics:**
- Sender does not wait for receiver to process
- Messages are queued and processed in order
- Can be used for cross-thread or cross-process communication

**References:**
- Enterprise Integration Patterns (Hohpe & Woolf): [Message Queue Pattern](https://www.enterpriseintegrationpatterns.com/patterns/messaging/MessageQueue.html)
- [Enterprise Integration Patterns Book](https://www.enterpriseintegrationpatterns.com/)
- Actor model: [Akka Documentation](https://akka.io/), [Erlang/OTP Documentation](https://www.erlang.org/doc/)

### 11.11 Script Isolation Patterns

For making non-thread-safe script interpreters safe in multi-threaded environments:

**Option A: Per-Thread Interpreters**
- Each worker thread has its own script interpreter instance
- Scripts run in the context of the worker thread
- Requires more memory but provides full isolation

**Option B: Dedicated Script Thread**
- Single thread owns the script interpreter
- All script requests are queued and processed sequentially
- Simpler but creates a bottleneck

**Option C: Script Batching**
- Collect script callbacks during the update cycle
- Execute them all on the main thread after other updates complete
- Maintains single-threaded script execution

**References:**
- Lua documentation on thread safety and multi-state usage:
  - [Lua 5.1 Manual - Coroutines](https://www.lua.org/manual/5.1/manual.html#2.11)
  - [Lua-Fiber: Coroutines for Multi-threading](https://github.com/stevedonovan/lua-fiber)
- Embedding script interpreters in multi-threaded applications:
  - [Lua State Management](https://www.lua.org/pil/29.html)
  - [Boost.Python GIL Handling](https://www.boost.org/doc/libs/release/libs/python/doc/html/python/threading.html)

### 11.12 Deadlock Detection and Prevention

**Concept:** Strategies for avoiding or detecting circular lock dependencies.

**Prevention Strategies:**
- Lock ordering: Always acquire locks in a consistent global order
- Lock timeouts: Attempt to acquire with timeout, back off on failure
- Lock hierarchy: Define levels, only acquire locks at higher levels

**Detection Strategies:**
- Wait-for graph analysis
- Timeout-based detection (if waiting too long, likely deadlocked)

**Existing Implementation in Codebase:**
- `src/server/database/Database/Transaction.cpp` - Deadlock retry logic with shared mutex

**References:**
- Goetz, B. et al. (2006). *Java Concurrency in Practice*. [Chapter 11: Deadlock](https://javaconcurrencyinpractice.com/)
- [Wikipedia: Deadlock](https://en.wikipedia.org/wiki/Deadlock)
- [C++ std::lock and std::lock_guard](https://en.cppreference.com/w/cpp/thread/lock)
- [Boost.Lockfree Documentation](https://www.boost.org/doc/libs/release/libs/lockfree/)

### 11.13 Stress Testing for Concurrency

**Concept:** Deliberately exercising code under high concurrent load to expose race conditions, deadlocks, and other threading bugs.

**Techniques:**
- Run tests many thousands of times with varying thread counts
- Introduce artificial delays to expose timing-dependent bugs
- Use thread sanitizers (TSan, Helgrind)
- Randomize operation ordering


**References:**
- Google Test framework: [Official Documentation](https://google.github.io/googletest/)

## 12. Glossary

| Term | Definition | References |

| **Atomic Operation** | An operation that completes indivisibly, visible to other threads as instantaneous | [cppreference - std::atomic](https://en.cppreference.com/w/cpp/atomic/atomic) |
| **Race Condition** | When program behavior depends on the relative timing of concurrent operations | [Wikipedia: Race Condition](https://en.wikipedia.org/wiki/Race_condition) |
| **Deadlock** | When two or more threads are waiting for each other indefinitely | [Wikipedia: Deadlock](https://en.wikipedia.org/wiki/Deadlock) |
